Why are server and browser results different?

Few server cores. Free cloud plans (like Render's free tier) give you a small share of one CPU. With one core the threads just take turns, so they can't run in parallel and every thread you create adds overhead. Speedup is close to 1× or below.

Your laptop has more. A typical laptop has 4–16 logical cores. The thread pool can keep all of them busy, so "My device" usually shows a real speedup for large matrices.

Thread start-up costs differ. A Node worker thread starts a whole new V8 engine (tens of ms). A browser Web Worker is often a bit cheaper. Either way, small matrices finish faster than a thread can even start.

All methods do exactly n³ multiply-adds. Threads don't reduce the total work. They only spread it across cores. tc is the cost of creating one thread. Every method also stores the three n×n matrices A, B, C (O(n²) space), shared by all threads through a SharedArrayBuffer instead of being copied.

Amdahl's Law, in simple words

S(p) = 1 / ((1 − f) + f / p)

Some fraction f of a program can run in parallel, and the rest (1 − f) has to run one step at a time. Even with unlimited cores, the one-at-a-time part still takes the same time. So the best possible speedup is 1 / (1 − f).

Matrix multiplication is almost entirely parallel (f ≈ 1), because every cell of C can be computed on its own. In practice, starting and stopping threads behaves like extra serial work. With small n that overhead takes up most of the time, so f is small and the threads don't help.

Theoretical vs actual speedup

Theoretical = min(threads, cores). That is the speedup you would get if creating threads cost nothing. Actual = what we measured. "Compute-only" leaves out thread creation.

05 · Learn

Theory

Everything you need to explain this project in your viva.

Matrix multiplication

For A (n×n) and B (n×n), each cell of the product is the dot product of a row of A and a column of B:

C[i][j] = Σk=0..n−1 A[i][k] · B[k][j]

There are n² cells and each one needs n multiply-adds, so the total is n³ operations, or O(n³) time. The three nested loops i → j → k are the classic algorithm.

Processes, threads & workers

A thread is an independent sequence of instructions inside a process. Threads in the same process can run on different CPU cores at the same moment. That is parallelism.

JavaScript runs on a single thread, so we use worker_threads in Node.js and Web Workers in the browser. Each worker is a real OS thread with its own JS engine.

Threads normally don't share variables, so we put the matrices in a SharedArrayBuffer and view it as a Float64Array. Every thread then reads A and B and writes its own part of C in the same memory, with no copying and no locks. No two threads ever write the same cell.

Creating a thread is not free. The OS has to set up a stack and the runtime starts a new engine. That cost, tc, is the main reason naïve threading loses.

Thread per row

n threads, each doing n² work. That is a reasonable amount of work per thread, but at n = 300 it means 300 threads fighting over a few cores, and 300 × tc of start-up time. That is why this method is capped at n ≤ 300.

Thread per cell

n² threads, each doing only n multiply-adds. At n = 10 that is 100 threads, each doing just 10 multiplications, which is far less than the cost of creating the thread. It is the clearest example of too many threads making things slower.

Optimized thread pool (the smart approach)

Create only p threads, where p is the number of CPU cores, and give each one a block of about n/p rows. Every core is busy, the start-up cost is paid only p times, and each thread works on rows that sit next to each other in memory. Once n is big enough that n³/p of work outweighs p·tc of start-up, this beats single-threaded. Real systems (Java's ExecutorService, OpenMP, Node's libuv pool) work the same way, and also reuse their threads.
